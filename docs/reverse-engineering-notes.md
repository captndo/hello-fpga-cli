# Reverse-engineering notes

This document records how the Hello FPGA stock PIC32 protocol was reconstructed, what is strongly established, and what remains uncertain.

It is intentionally separate from the protocol specifications so that implementation facts are not mixed with investigative history.

## Evidence sources

The work used three main evidence classes:

1. **Official-GUI traffic captures** — USB/serial traffic generated by the legacy Hello FPGA GUI.
2. **Factory PIC32 firmware static analysis** — Intel HEX imported into Ghidra and decompiled as MIPS32 little-endian code.
3. **Active host reimplementation** — Python code replaying the reconstructed protocol successfully against the board.

Additional supporting material included the Hello FPGA project RTL, the recovered Windows-side `spi_loader.c`, board schematic/design documentation, and DirectC documentation.

## Confidence labels

When extending these notes, use labels such as:

- **CAPTURE-CONFIRMED** — directly observed in official-GUI traffic.
- **STATIC-CONFIRMED** — directly visible in stock firmware code/data.
- **ACTIVE-REPLAY-CONFIRMED** — reproduced successfully by the custom host.
- **LIKELY** — strong evidence but one important link remains unverified.
- **GUESS** — working hypothesis only.

## Firmware architecture

The studied board contains a separate PIC32MX795F512L management MCU in addition to the SmartFusion2 SoC FPGA.

The PIC32 uses a MIPS32 M4K core and should be imported into Ghidra as:

```text
MIPS / default / 32-bit / little-endian / default compiler
```

Do not select Ghidra's small-PIC processor families.

### Flash mapping

The Intel HEX was imported at physical program-flash addresses beginning around:

```text
0x1D000000
```

The corresponding normal KSEG0 virtual alias is:

```text
0x9D000000
```

Boot flash uses the analogous mapping:

```text
physical  0x1FC00000
virtual   0xBFC00000
```

A byte-mapped Ghidra block for the `0x9D...` alias is useful because code pointers in the firmware use virtual addresses.

The studied application image occupied roughly `0x9BA0` bytes beginning at `0x1D000000` in the imported image, plus boot-flash content.

## Key recovered functions

The following names are suggested reverse-engineering labels, not original source symbols.

### Main state machine — `FUN_9d001898`

Recovered high-level states:

```text
0 initialization
1 idle / dispatcher service
2 DirectC
3 common UART bridge
4 power/PAC1710
5 FlashFreeze enter
6 FlashFreeze exit/timing
```

### Idle dispatcher — `FUN_9d0031e8`

This was the decisive function for the top-level protocol. It reads one host byte, echoes it, and switches on exactly:

```text
0x21  '!'
0x23  '#'
0x24  '$'
0x26  '&'
0x2A  '*'
0x40  '@'
```

Assignments from that switch directly identify the state selected by each command.

### Common bridge body — code beginning at `0x9D001908` / `FUN_9d001aa8`

Ghidra initially split the bridge body in an awkward way and reported several `unaff_s*` registers. Inspecting the preceding case setup resolved them:

```asm
clear s0
li    s4,0x25    ; '%'
li    s3,0x45    ; 'E'
li    s2,0x78    ; 'x'
```

This confirmed the `%Ex` escape prefix statically.

After `%Ex`, the code calls a host-read helper with length `3`, then returns the main state to `1`.

### Host exact-read helper — `FUN_9d007a80`

This function repeatedly polls the selected host serial channel, reads bytes, and stores exactly the requested count into the supplied buffer.

It does not validate the contents. This is why the bridge condition is `%Ex` plus any three consumed bytes, even though the official GUI sends `%ExIt3`.

### DirectC host handshake — `FUN_9d006790`

Recovered exchanges:

```text
s -> h
a -> k
e -> r
```

### DirectC action reader — `FUN_9d007d5c`

The compiler built an unusual stack lookup table, but the indices line up exactly with ASCII `'1'..'7'`:

```text
'1' -> 1
'2' -> 2
'3' -> 3
'4' -> 5
'5' -> 6
'6' -> 7
'7' -> 28
```

The PIC sends `'A'` before reading this selector.

### DirectC family reader — `FUN_9d008fe0`

The PIC sends `'F'`, reads one ASCII byte, subtracts `'0'`, and stores the resulting numeric family value.

The official GUI sends `'5'`, and the later identification routine uses value 5 on the SmartFusion2/IGLOO2 path.

### DirectC device identification — `FUN_9d007160`

This routine emits text including:

```text
Identifying device...
Looking for M2S/M2GL device...
```

It is device setup/identification, not the action dispatcher.

### DirectC action dispatcher — `FUN_9d004740`

This directly dispatches the numeric action global:

```text
1   -> FUN_9d00821c
2   -> FUN_9d009b3c
3   -> FUN_9d007950
5   -> FUN_9d004b70
6   -> FUN_9d004cb4
7   -> FUN_9d0084fc
28  -> FUN_9d001410
```

These align with device info, IDCODE, erase, program, verify, encrypted-data authentication, and digest verification.

### Power handler — `FUN_9d003d58`

This performs sensor transactions and serializes exactly seven response bytes. The final three fields match the PAC1710 product ID `0x58`, Microchip manufacturer ID `0x5D`, and `0x61` terminator seen in captures.

### FlashFreeze exit — `FUN_9d004a10`

This configures/reads a counter around a hardware transition, computes the difference, and serializes four bytes little-endian. This statically confirms the host interpretation of the wake-up payload as `u32le` ticks.

## DirectC runtime capture findings

Successful official-GUI programming captures showed the following PIC-driven records:

```text
P  text/status
D  DAT slice request
R  raw progress byte
T  transition marker
```

`D` requests matched exact slices of the DAT file. Requests were typically bounded to 1024 bytes and the final response was a genuine short chunk rather than padded data.

A successful programming run can become silent for more than ten seconds after `R=100`. This drove the host design toward a long idle timeout rather than using progress completion as a terminal condition.

Completion is based on DirectC text containing both an `Exit code = ...` result and the `End DirectC Demo...` marker.

## UART abstraction clues

Several wrapper functions select between channel `0` and channel `1`, then call one of two low-level serial implementations. This supports the architectural model of one PIC serial path facing the host and another facing the FPGA.

The exact PIC32 UART peripheral numbers, BRG values, and FPGA-side baud configuration have not yet been completely mapped in this work. Those details are useful for board-plumbing completeness but are not required by the current PC host protocol implementation.

## GPIO/SFR clues

Static analysis identified PIC32 SFR writes in the `0xBF886xxx` region using the standard PIC32 `CLR/SET/INV` shadow-register pattern.

Examples around bridge and FlashFreeze behavior appear to affect individual PORTA/PORTD latch bits. Mapping those bits to schematic net names would tell us exactly which mux/reset/control signals are asserted by each mode.

This remains useful future work, especially for understanding the unsupported `!` bridge mode, but it is not a prerequisite for operating the supported host protocol.

## FPGA-side FIR investigation

The FIR demo was useful for separating protocol layers:

```text
PC protocol layer      '&' bridge entry / '%ExIt3' exit
PIC bridge layer       raw byte forwarding
FPGA application       h/a/r/i + coefficients/samples/results
```

The recovered FPGA RTL showed that the demo fabric protocol itself accepts 16 unique coefficients for a 31-tap symmetric FIR, then 1024 input samples. The vendor GUI sends 31 coefficients, causing the latter 15 coefficients to be interpreted as the beginning of input data by that specific demo RTL.

This is an application-level demo mismatch, not part of the PIC bridge protocol. It is intentionally excluded from the general bridge API.

## Current unresolved questions

The remaining uncertainties are mostly below the host-protocol layer:

- exact physical PIC UART mapping and FPGA-side UART configuration;
- exact schematic meaning of all GPIO/control writes;
- exact PAC1710 configuration written by firmware before measurement;
- FlashFreeze counter clock / conversion from ticks to time;
- exhaustive behavior of every partial/mismatched `%Ex` escape prefix;
- complete behavior and recovery semantics of the unsupported `!` bridge mode;
- boot-flash/startup helpers not needed by normal host operation.

## What not to over-interpret

Finding a function in the firmware does not mean it is host-accessible.

When documenting future discoveries, distinguish:

```text
implemented in firmware
reachable during normal execution
reachable from a top-level host command
used by the official GUI
```

Only the first of these follows from finding code in the HEX image.
